# Codex reviews and design debate, 2026-10-10

Three read-only Codex (GPT Astra, high) rounds on the Wi-Fi Aware work, plus a two-round adversarial design
debate on the connection setting. Full briefs, final messages, event logs, the device logs and the reviewed
patch live outside the repo at `~/Documents/open-source-selfie-stick-codex/2026-10-10/` on the build Mac.
This file keeps the decisions: each finding with its disposition.

## Design debate outcome

Round 1 attacked the lead's proposal (automatic Wi-Fi Aware fast lane negotiated over Bluetooth) and ranked
five options; round 2 settled the mechanism. Result: option C, no user-facing connection choice, Release always
`LayeredTransport`, Debug-only internal test switch, Release metadata stripped; option D recorded in
TRANSPORT.md as the way Wi-Fi Aware returns. See TRANSPORT.md § "why it left the shipping app".

## Reliability + App Store review, round 1

Artifacts: review-r1.brief.txt, review-r1.events.txt, review-r1.final.md; logs/ (four device logs);
working-tree.patch (the diff reviewed). All code changes below are in the working tree, uncommitted.

A1 Discovery restarts before cancellation completes — ACCEPTED. Cancelled listener/browser tasks are kept in
   `retiringTasks`; a replacement `runListener`/`runBrowser` awaits them before touching the service. A session
   that ended by failure also delays the next listener ~2 s (+0–0.5 s jitter).
A2 Old pairing handoff can resume a newer suspension — ACCEPTED. `suspendForPairing()` returns a generation
   token; `resumeAfterPairing(token:)` is a no-op for anyone but the current owner. `WiFiAwarePairingState`
   stores and passes its token, including on the cancelled-while-suspending path.
A3 Reconnect identifies the camera by name — ACCEPTED IN PART. `RemoteModel` now remembers the peer id and
   matches it first; the display name stays as a fallback because Multipeer/Bluetooth peer ids are not stable
   across sessions on every transport. Test `reconnectMatchesTheCameraByIdBeforeName`.
A4 Timeout path can mistake an old disconnect for the new attempt's failure — ACCEPTED. A timed-out reconnect
   attempt no longer re-invites immediately: it records the attempt's peer, cancels it, and the transport's late
   `.disconnected` for that peer starts the next try (a 1 s fallback covers transports that never send it).
   Test `aLateDisconnectFromATimedOutAttemptStartsTheNextTryOnce` keeps the camera discovered.
A5 Readiness races the transport timeout — ACCEPTED. `connectionTimedOut` now calls `finishSession(onlyIfUnready:)`
   so the readiness check and the teardown share one lock acquisition.
Keepalive — ACCEPTED (not shipping one). Idle closure is treated as recoverable; reconnect on demand. The DPLA
   clause you quoted is the deciding reason.
Typed error — ACCEPTED. Listener/browser/connection failures now log `NWError.wifiAware` (WAError) so the next
   run names the timeout (publisherTimeout / connectionIdleTimeout / …) instead of -11989.
Retry policy — ACCEPTED IN PART. Wi-Fi Aware: 10 s attempts, 5 tries; camera re-listens after ≥2 s following a
   failure; fresh browse results only (the picker-endpoint path is gone). Bluetooth keeps 30 s / 3 tries (verified
   on hardware). No 120 s overall deadline yet; the attempt budget bounds it (~60 s plus discovery).
Accepted-connection survival — ACCEPTED (no change). The connection stays inside the listener handler; the
   framework ending it is recovered by reconnecting.
B6 / C10 Recording loses Stop when the remote drops — ACCEPTED. The camera keeps the viewfinder and controls while
   `state.isRecording`, in both transports; the waiting room returns once recording stops.
B7 Awaiting a picked camera can wait forever — ACCEPTED. After 15 s the remote shows what to check and a
   "Stop waiting" button wired to `cancelAwaiting()`.
B8 Camera copy promises auto-continue when re-pairing — ACCEPTED. Copy depends on `hasPaired`; the button is
   "Done pairing" on both screens.
B9 Setup copy promises standalone capture — ACCEPTED. Reworded: viewfinder and shutter appear once a remote is
   connected.
Mixed-pair help line — ACCEPTED. "If either device has no Wi-Fi Aware option, use Automatic on both."

## Reliability review, round 2

1a Retiring task can await itself — ACCEPTED. Discovery tasks now receive their own handle (`TaskBox`) and
   `awaitRetiringTasks(excluding:)` skips it; tasks stay in `retiringTasks` until awaited (pruned after), and
   a superseded task exits before touching the service.
1b Outgoing connection teardown not in the barrier — ACCEPTED. `finishSession` and `suspendForPairing` retire
   `connectionTask` too; the next browser/listener awaits it.
1c Listener failure can bypass the back-off — ACCEPTED. `lastFailureAt` is recorded in the listener's
   `.failed` state callback, before the accepted session unwinds.
2  Newer handoff can mount pairing before the older teardown finishes — ACCEPTED. `suspendForPairing` no
   longer drains the tasks into a local array; it retires them into the shared `retiringTasks` and awaits a
   snapshot, so suspension B awaits whatever A left unwinding.
3  A4 schedules — ACCEPTED IN PART. Schedule (a) (timeout → rediscovery → re-invite → old disconnect) was
   already closed when you reviewed: `attemptReconnect` is gated on `staleAttemptPeerID == nil` (the patch you
   read predates that edit); test `rediscoveryDuringATimedOutAttemptsTeardownDoesNotOpenASecondAttempt` holds
   the fake's disconnect back explicitly and delivers it after rediscovery. Schedule (b) (disconnect later than
   the 1 s fallback) — REJECTED as unreachable with the shipped transports: `WiFiAwareTransport.disconnect()`
   yields `.disconnected` synchronously into the event stream (milliseconds), and `BluetoothTransport` tears
   a pending invite down with `notify: false`, i.e. never. The fallback exists for the Bluetooth case. Noted in
   code and docs; attempt-tagged events are the proper fix if a third transport appears.
   A3 wording — ACCEPTED: id-only matching whenever an id was recorded.
   "Reconnect on demand" wording and "budget bounds elapsed time" — ACCEPTED: docs now say automatic retries
   start immediately on an unexpected drop, that waiting for rediscovery is unbounded, and that a
   discovery-inclusive deadline is required before Wi-Fi Aware ships publicly.
4  Waiting room can flash during recording start-up — ACCEPTED. The viewfinder also stays while
   `state.isBusy` (a capture starting or finishing).
5  No finding — noted.

## QR-code pairing idea (one adversarial round, evening)

Rich's idea: both phones scan each other's QR; the QR carries a Wi-Fi Aware capability bit; two true bits
pick the Wi-Fi Aware route, otherwise the QR replaces the four-digit code. Claude's version: one-way scan
(remote scans camera), 128-bit secret replacing the code with manual digits kept, capability bit feeds design
D rather than choosing the transport, universal-link QR so the system Camera app opens the app without a
camera permission on the remote.

Codex's ranking: (1) keep four-digit pairing for this release; (2) later, an optional one-way in-app scan
after selecting the camera from the list, with manual digits always available, an independent 128-bit
invitation id + secret (`SC1:<id>:<secret>`, 49 bytes), a reciprocal camera proof added to the handshake,
no capability bit, no transport selection; (3) Claude's version (automatic peer selection needs a Bluetooth
advertising design that Core Bluetooth's name + service UUID cannot carry; a universal link puts a credential
in a URL and backgrounds the remote); (4) the idea as stated (two scans add work without information that
needs an optical channel; two capability bits do not establish that Wi-Fi Aware will work; replacing manual
entry excludes working remotes; a QR is an encoding, not an authentication design). Estimated 850–1,400
production lines plus tests for (2). Dispositions: ACCEPTED as the plan of record; nothing built.

Two source-level findings from that round, both ACCEPTED and fixed the same evening: the camera left the
waiting room on `link.isConnected`, i.e. before the code was proven, so an unauthenticated Bluetooth
connection showed the viewfinder (now gated on the paired state); comments claiming the Bluetooth channel is
encrypted were stale (the L2CAP channel is opened without encryption; README already says the code is not
designed to resist sniffing).

## Remote live view (liveview-r1, GPT Astra high, read-only)

Rich's idea, after agreeing Wi-Fi Aware is more trouble than it is worth for this app: stream a low-quality
live view from the camera to the remote (originally to keep a Wi-Fi Aware link non-idle; the motive that
survived is the product one — the remote frames blind). Claude's opening position: JPEG frames, not video;
two tiers chosen by the lane (Wi-Fi ≈480 px/10 fps, Bluetooth-only 240 px/1 fps "framing frames" under a
quarter of the 28 KB/s budget); pull-based start/stop; rotation as metadata; no new permission.

Codex's ranking: (1) a narrower version, after the current work is committed and verified on hardware:
Wi-Fi-only, demand-driven (the remote requests one frame at a time over a new binary lane 2 on the Wi-Fi
leg; nothing queues; preview send never falls back to Bluetooth), ≈480 px/5 fps/32 KiB cap, degrade to
320 px/2 fps under congestion or thermal pressure, pause during file transfers, subscription accepted only
after `isPaired`, orientation and mirroring baked in at the camera, wire version bump to 4; (2) Claude's
two-tier version later, if Bluetooth latency tests earn the fallback; (3) don't build it; (4) build it now.
Objections accepted: `L2CAPStreamHandler` has a single outbox with no priority, so a 5–6 KB frame blocks
the lane for ~180–215 ms and "under a quarter of the budget" does not establish shutter latency; reliable
Multipeer sends queue without backpressure, so independent JPEGs stop corruption but not latency build-up;
5 KB at 240 px is a silhouette, not a face; `startPreview`/`stopPreview` is subscription control, not flow
control (the stop may never arrive); rotation degrees omit mirroring and aspect-fill cropping; "leaves no
trace" is an overclaim (screenshots on the remote) and guideline 2.5.14 wants a visible sharing indicator;
don't use `systemUptime`/`mach_absolute_time` for frame timing (required-reason API). Shipping without
remote focus/zoom is a complete framing feature. Keep the camera's own preview on in v1.
Dispositions: ACCEPTED as the plan of record, recorded in docs/TODO.md; nothing built; DESIGN.md's
out-of-scope line is replaced in the feature change, not in the stabilisation commit.
Artifacts: liveview-r1.{brief.txt,final.md,events.txt} in ~/Documents/open-source-selfie-stick-codex/2026-10-10/.
